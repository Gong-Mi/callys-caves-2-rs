# 原生库逆向的问题、退出条件与方法

本文件固定本线交付对象与完成含义。实现细节可以修正，但不能用另一个目标或另一种数字替换本问题。

## 0. 本轮固定的问题与阶段门

问题是：对 SHA256 `3bbedd09ad0cc60f3f3cad86a257275f841d3910c11f05985bcaecc6bc0fbe3a`
的原版 ARM32 `libyoyo.so`，恢复完整库内代码的函数语义、数据布局及调用合同，落成可审计、
可编译的 C 译文。不是再造一个能运行游戏的近似引擎，也不是把已有反汇编注释重新计数。

范围固定为完整库，包括引擎、平台桥、错误/失败支路、初始化/终结、静态链接第三方库和
尚未定界的匿名区域；不能用游戏入口的可达子集替换全库。ELF 导入的 libc/GL 等库外实现
不要求在本库重写，但调用 ABI、参数、返回/失败与副作用边界必须写清；库内未恢复 helper
不能伪装成永久外部依赖。PLT/别名另行归类，不重复计作业务函数。

当前顺序：先完成全库静态语义与译文，再进入原件同输入对照。此阶段允许编译、运行重建
C 及具名合成边界检查来找译文自身的错；不执行原件、不扩建 ART/Unicorn/游戏启动环境，
也不以截图、APK 运行或 C↔Rust 自洽替代原生逆向。

每个函数分别记录两个轴（不得压成卡片等级）：

- 语义：未审 / 结构已知 / 部分语义 / 静态闭合。
- 译文：无本体 / 部分本体 / 完整可编译本体。

一个函数只有同时交齐下列内容，才可标为本阶段“完成”：

1. 样本哈希、地址、ARM/Thumb 模式和可信边界；同址别名合并，不以候选匿名段冒充函数。
2. ABI：全部参数/返回、隐式 this/sret、宽度、有符号性、栈参数和函数指针合同。
3. 全部可达控制/数据路径：分支、循环、提前退出、失败/异常、数值截断/回绕和外调前后重读。
4. 结构/全局量的字段布局、读写/所有权和相关副作用；未知项具体写出，不用名字猜含义。
5. 可直接回查原件的语义说明及真实 C 函数体；注释汇编、自动骨架、声明、空桩不算本体。
6. 逐项列出内部与外部依赖及间接调用目标；未定目标、未明边界或未闭合路径保留为阻塞项。
7. 静态锚点/操作数和编译检查通过；合成用例只证所检查的译文合同，不升级为原版等价。

全库退出条件是：所有已知唯一入口和全部匿名候选区域均完成边界归属对账，并逐函数满足
上述七项，未闭合函数/匿名边界/内部依赖为零。人口尚未收敛时不报总语义完成率。
锚点满覆盖、卡数、测试数和若干函数交付都不能触发全库完成。

推进单位为完整函数及其直接依赖。先收共享语义基础件和已接入链上的内部缺口，再扩调用者；
夹具/审查只服务于这批函数，不把本线变成长期验收框架建设。默认本地提交，不推送。

## 1. 证据分层（不许混报）

    bytecode_anchored  每条指令都锚到二进制里的同一条指令，语义从 asm 推出
    oracle_anchored    与原版运行时/活体的数据对过（实例表/房间表 → 活体读内存；处理器语义 → 原版函数在
                       Unicorn 里执行后与 C 重建逐例对拍，见 reconstruction/reverse-v1/harness/）
    test_anchored      只证明"两个自研实现互相一致"（C↔VM 差分属于这一层）
    host_authored      手写实现，没有原版对应（c-recon/src/*.c 属于这一层）

一条主张只能落在其中一层；**跨层升格必须补证据**，不能因为"看起来对"就往上写。

## 2. 锚点

    索引来源      scripts/asm_index.py 从 .so 生成（addr/word/mnem/operands），不接受手抄
    卡片格式      每条指令一行 `/* @0x<addr> <mnem> <operands> */`，操作数与索引逐字一致
    单卡校验      scripts/check_card_anchors.py → 必须 RESULT EXACT（缺/多/错操作数都算失败）
    全库校验      scripts/verify_reverse_v1.py → 对全局 instructions.jsonl(.xz) 逐地址比
    锚点写法      `/* @0x…` 与块注释内的 `* @0x…` 都接受（verify 的正则会两种都认）

## 3. ISA（ARM vs Thumb-2）

    .dynsym 的 st_value 为奇数 = Thumb-2（bit0 是 ISA 选择位）；地址要 &~1 归一
    无名 Thumb 不能靠"解码看起来像什么"判：0x2f8e0a 的 ARM 视图与 Thumb 视图都"看着合理"
    唯一可靠判据是**调用点编码**：`bl`/`blx` 状态保持 —— ARM bl 命中 0 且 Thumb bl 命中数与该段
      in-degree 逐字相同，才能定 Thumb；判定的段写进 asm/thumb_ranges_extra.txt，由 census 重解

## 4. 匿名区

    切分用三个信号（缺一不可）：bl 直接目标 / ARM prologue（push{...,lr}）/ .data·.rodata 里的
      数据指针（方法表入口，必须先过滤"落在指令边界上"，且 Thumb 指针要 &~1）
    段长 ≠ 函数长度：段长是"到下一个切分点的距离"；0x2f8e0a 的段 1,170 B 里入口只有 28 B
    无名段只能叫 anon_<addr>，级别最多骨架；不许给它编名字

## 5. 人口与覆盖口径（不得互相替代）

    原版 ELF       9,267 条已定义可执行 STT_FUNC 符号；按规范化地址+ISA 合并为 8,926 个入口，
                   多出的 341 条是别名行，不等于新增函数。
    既有索引       functions.tsv 共 9,538 行、9,199 个起址，其中 272 行是 anon_ 合并区间；
                   anon_splits.tsv 现有 646 个候选段，不能再加到符号数上当真实函数分母。
    解码索引       649,229 个去重地址条目，包含 literal pool 的解码项；索引满锚不等于全部为指令。
    语义与译文     分别按第0节逐函数七项合同登记；卡头“正文”、@func 主张区间及整段计入的旧上限
                   估计均不作为完成证据。尚无可信全量静态闭合率，不给替代百分比。
    三种数量       生成能力、已提交本体、已静态闭合函数分账；同址别名、匿名候选、骨架不得混算。

## 6. 差分（C 参考实现 ↔ Rust VM）

    协议          reconstruction/contracts/opcode-diff-protocol.md（JSONL 逐行）
    用例          diff/gen_cases.py，种子 0xCA11，22 op × 200 = 4,400
    C 侧          diff/c/vm_ref.c，tier: host_authored，语义按卡
    Rust 侧       crates/core/examples/op_eval.rs，走真 VM（code_vm），不改库以迁就对比
    判据          ok / sp / result.bytes / result.tag / error 逐字段相等
    禁止          为了对齐而伪造 tag、用 ×16 换算 sp（已实测 −4 会变 −256）、
                  把"两边都能跑"当成等价

## 7. 交付与并发（踩过的坑）

    子代理并发上限 4（10 并发会把父进程打满，整批 0 交付，已发生两次）
    子代理必须增量落盘：卡头 + 第一节 → check → 落盘 → 追加；不许算完全部才写
    验收只看盘：git status + verify_reverse_v1；不信子代理自述（两次事故里自述都像"完成"）

## 8. 明确不做

    不驱动原版 app 逐帧操作（慢、不可复现）
    不用截图/像素当语义判据（像素是下游消费）
    不给无名函数编名字
    不把"我实现了"说成"原版是这样"
